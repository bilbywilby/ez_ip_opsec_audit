6. Disaster Recovery

6.1 Objectives

Tier Component RPO RTO
1 Database (findings, audit cycles) 24h from logical dumps alone; ~5 min only with RDS automated backups or WAL archiving (see 6.4a) 2h
2 Dashboard + scheduler n/a (stateless) 1h
3 Logs / audit artifacts 24h 8h

pg_dump/pg_restore is logical and restores to the moment of the dump only. It cannot give point-in-time recovery. PITR needs a physical base backup plus continuous WAL archiving (RDS automated backups do this for you). Without one of those, the RPO is 24h.

6.2 What is backed up

  • PostgreSQL dump (pg_dump --format=custom), encrypted
  • Findings JSON export (90 days)
  • Archived logs
  • Config and secrets: in your secret manager, not in backups
  • Terraform state: S3 with versioning on

6.3 Disaster scenarios

Scenario Recovery path
Single container/host failure Restart; ASG/compose restart: unless-stopped
Database corruption PITR to just before the corruption (6.4a), or restore latest dump (6.4) and accept loss since the dump
Region/AZ outage Re-apply Terraform in alternate region, restore DB from cross-region backup copy
Ransomware / compromise Treat as breach (Scenario C). Rebuild from clean images, restore DB from a backup that predates compromise, rotate every secret
Accidental deletion Restore from backup; for repo, git reflog / remote

6.4 Database restore

Backups are created with pg_dump --format=custom, so restore with pg_restore, not psql.

# 1. Pick and verify backup
ls -t /mnt/backups/security-audit/database/ | head
openssl enc -d -aes-256-cbc -pbkdf2 -pass file:/etc/security-audit/backup.key \
  -in <backup>.gz.enc -out /tmp/restore.dump.gz
gunzip /tmp/restore.dump.gz

# 2. Restore into a NEW database first
createdb -h "$DB_HOST" -U "$DB_USER" security_audit_restore
pg_restore -h "$DB_HOST" -U "$DB_USER" -d security_audit_restore --no-owner /tmp/restore.dump

# 3. Sanity check
psql -h "$DB_HOST" -U "$DB_USER" -d security_audit_restore \
  -c "SELECT COUNT(*) FROM audit_cycles; SELECT COUNT(*) FROM findings;"

# 4. Cut over: stop app, rename databases, start app
docker compose stop dashboard scheduler
psql -h "$DB_HOST" -U "$DB_USER" -d postgres -c \
  "ALTER DATABASE security_audit RENAME TO security_audit_old; \
   ALTER DATABASE security_audit_restore RENAME TO security_audit;"
docker compose up -d

# 5. Verify
curl -sf https://security-audit.example.com/api/status | jq .
shred -u /tmp/restore.dump

Keep security_audit_old until the incident is closed.

6.4a Point-in-time recovery (RDS)

Production DB is RDS (main.tf). PITR needs automated backups on (backup_retention_period >= 1; Terraform sets 7 for prod, 1 otherwise). pg_dump cannot do PITR.

# Read-only preflight: checks source, retention window, target time; prints the command
./scripts/restore_db_rds.sh --target-time 2026-10-04T12:00:00Z --dry-run

# Restore into a NEW private instance (asks for confirmation)
./scripts/restore_db_rds.sh --target-time 2026-10-04T12:00:00Z

The script never touches the source instance, Terraform state, or running containers. Afterwards:

  1. Validate row counts on the new endpoint.
  2. Update the DB URL in the secret manager, then restart dashboard and scheduler.
  3. Keep the old instance until the incident is closed.
  4. Reconcile Terraform deliberately (import or rename). Never from a restore script.

If Postgres also runs as a Compose service, this section does not cover it. Remove the db service from docker compose.yml so the two cannot diverge.

6.5 Full rebuild (host/region loss)

Region loss prerequisite: PITR cannot cross regions and a dead region takes its automated backups with it. Replicated backups must already exist:

# Run in the DR region, ahead of time
aws rds start-db-instance-automated-backups-replication --region <DR_REGION> \
  --source-db-instance-arn <source instance ARN> --backup-retention-period 7
# add --kms-key-id <key in DR region> if the source is encrypted

Without this, the database RPO for a region loss is the last off-region copy of a dump.

  1. cd terraform && terraform init && terraform apply -var environment=prod -var aws_region=<DR_REGION>. This also creates an empty RDS instance; delete it once the restored one is up.
  2. Restore the database from the replicated backup: 
    aws rds restore-db-instance-to-point-in-time --region <DR_REGION> \
  --source-db-instance-automated-backups-arn <replicated backups ARN> \
  --target-db-instance-identifier security-audit-dr-$(date -u +%Y%m%d) \
  --use-latest-restorable-time --no-publicly-accessible \
  --db-subnet-group-name <subnet group> --vpc-security-group-ids <sg ids>
    Same-region host loss: use ./scripts/restore_db_rds.sh instead.
  3. Put the new DB URL in the secret manager, then DEPLOY_ENV=production ./scripts/deploy.sh deploy.
  4. Re-point DNS (lower TTL to 60s in advance if you can).
  5. Confirm Prometheus targets are up and alerts route to Slack/email.
